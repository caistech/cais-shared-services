# Shared Services Catalog — what's available to consume (read before building)

> **Purpose.** This is the portfolio's **single capability index of the `@caistech/*` shared
> substrate.** Read it before building anything non-trivial, so you *consume* an existing shared
> service instead of re-forking one (the `@caistech`-first rule + the fork-check guard exist
> precisely to stop the second person rebuilding what the first already extracted). If a capability
> below covers your need, install and consume it — do not hand-roll a local copy.
>
> **It is auto-loaded every session** (imported by the global CLAUDE.md, the same mechanism that
> loads `BUSINESS_MODEL.md` + `PRODUCT_STANDARDS.md`), so every agent in any repo starts knowing
> what the substrate already offers.
>
> **Maintenance rule (non-negotiable).** When you **add a new `@caistech/*` package** or **extend an
> existing one with a notable capability**, update this catalog in the SAME change — a shared service
> that isn't listed here is invisible to every future session and *will* get re-forked. Keep entries
> one-line and capability-focused. Source of truth for each line is the package's own
> `package.json` description; regenerate the bulk of this file from those descriptions if it drifts.
>
> **Standing rule — convergent shape, then extract (the "build-alike" rule) [non-negotiable].** When
> you build a capability a SIBLING product already has and **no `@caistech/*` package exists yet**,
> build the new one to the **SAME SHAPE** as the existing implementation — mirror its exported types,
> field names, function signatures, and UX — rather than a divergent design. The **2nd occurrence is
> the extraction trigger** (`BUSINESS_MODEL.md` §6); this rule is its *precondition*: convergent
> implementations make the eventual `@caistech` extraction a **lift**, divergent ones force a
> **rewrite** and quietly defeat the extraction detector + the fork-check. Applies to engines, data
> shapes, **and UI components** (e.g. a product's cost dashboard mirrors the cockpit's
> `UsageAnalytics` shape so the two can later collapse into ONE shared component). Consume-first (the
> `@caistech`-first rule) still wins whenever the package already exists; this governs the case where
> it does **not** yet — build it *alignable*, so bringing it in as canonical is mechanical.
>
> **Install:** registry is GitHub Packages (`@caistech:registry=https://npm.pkg.github.com`, token
> `NODE_AUTH_TOKEN`/`GITHUB_PACKAGES_TOKEN`). `npm install @caistech/<name>`. Consumers import the
> compiled `dist/`, never source. **Last updated:** 2026-07-31 (53 packages).
>
> **OPEN EXTRACTION CANDIDATES — second occurrence reached, package not yet built.** Listed here so a
> third implementation is a deliberate choice rather than an accident:
> - **`@caistech/google-workspace`** (Drive + Gmail + Contacts over one OAuth client). Two live
>   implementations: **F2K-Checkpoint** `src/lib/drive/client.ts` (single identity, one script-minted
>   refresh token in env — right for one company's own mailbox) and **orchestrator**
>   `src/connectors/google.ts` (multi-tenant, per-owner consent, tokens in `connections`). Checkpoint's
>   is the more mature client; the orchestrator's is the correct tenancy model. Setup shape, scope set
>   and the silent-failure traps are canonical in **`GOOGLE_WORKSPACE_CONNECTOR.md`** — read it before
>   writing any Google integration.
> - **Conversational, effect-asserted red-teaming** → belongs INSIDE
>   `@caistech/security-gate/red-team`, which already exists and which **Kira did not consume** (it
>   built `scripts/red-team.mjs` + `lib/kira/redteam.test.ts` + its own tables instead — an
>   `@caistech`-first miss the fork-check did not catch). They are not duplicates: security-gate's
>   `Probe` is **single-turn** and scores the **response text** with `failureIndicators: RegExp[]`,
>   while Kira's is **multi-turn** and takes its verdict from **observed side-effects** (DB state
>   before/after). *Does this endpoint say something it shouldn't* vs *can this agent be talked into
>   doing something it shouldn't* — and for an agent holding a real person's Drive, contacts and mail
>   the second is the one that matters, because an agent that says the right thing and does the wrong
>   one passes a regex and fails the customer. **Full directive:
>   `packages/security-gate/RED_TEAM_CANONICAL.md`** — adds `ConversationProbe`, a transport seam, a
>   non-negotiable synthetic-subject contract (Kira's first run pointed at the LIVE owner's account
>   and was saved by an unrelated 403), and pass-RATE-over-time instead of `regression: boolean`,
>   because these suites are non-deterministic. ⚠️ Two live consumers (SayFix, platform-trust) — the
>   no-orphaned-consumers rule applies to every type change.
> - **Document text extraction** (PDF/docx/xlsx → text). Belongs in `@caistech/dataroom-core`'s
>   already-documented-but-unshipped `/ingest` subpath, NOT forked per product.
>   `@caistech/document-ingest` is not it — that one is specialised to AU subdivision approvals.

Config resolves CLI flag → env → `.vercel/project.json`; `--wait` polls until a push's build settles. Wired into `templates/.github/workflows/gate.yml` on push/schedule (not PRs — it judges *production*), with the same loud `::warning` on an older installed version. **v0.10.0 adds `portfolio-gate-audit-machine-routes`** — *does the middleware matcher silently swallow the routes MACHINES call?* A session-refresh middleware redirects anything without a session, and a Next matcher normally runs on everything, so a vendor webhook or cron route is **307'd to /login unless explicitly excluded** — and a redirect is not an error, so nothing throws, nothing logs, the caller often follows it to a 200 HTML page, and the feature simply never runs. **ExecutorAI lost the same feature to this twice in one day**: every ElevenLabs call to its convai webhooks (no voice memory was ever written or read), then every scheduled retention purge. Both looked healthy from outside. The cause is structural rather than careless — the exclusion lives in a regex in `middleware.ts`, far from the route that depends on it — so the check moves the requirement **onto the route**: mark it `@machine-callable` and the audit fails if the matcher still captures it. **Scope is deliberately narrow and stated:** it only checks *marked* routes, because "is this called by a browser?" is not statically decidable; the marker is still something a person must remember, but it is small, local, and in the file they are already editing. **SKIPS (not fails) with no middleware or no marked routes** — both are genuine non-applicability, unlike a missing config — and **warns rather than passing** when the matcher cannot be parsed, refusing to report a verdict it did not establish. Verified by reintroducing the real bug: removing one exclusion flipped it to exit 1 naming the exact route, restoring it returned exit 0. Wired into `templates/.github/workflows/gate.yml`. **v0.11.0 adds `portfolio-gate-audit-public-routes` — the BROWSER-facing twin: can a visitor with no session actually open the pages we publish?** Machine-routes covers webhooks and crons; the identical structural failure hits **public marketing pages**, and it is worse there because it is customer-visible. ExecutorAI shipped `/for-advisers` without adding it to the middleware's public allowlist, so every visitor was 307'd to `/login` — and **the entire verification stack went green over it**: `curl -L` *followed* the redirect and returned **200**; the deploy gate's `--app-marker` assertion *matched*, because the login page carries the product name too; and `deploy-status` *passed*, correctly, since production genuinely was serving the expected SHA. Status-code checks, marker checks and deploy-SHA checks can therefore all pass over a page nobody can open. **`redirect: 'manual'` is the whole check** — following the redirect is precisely what hides the bug. Mark a page `@public-route`; the audit probes each without following redirects, FAILS on a 3xx (naming the status *and* the Location, since "307 → /login" is the diagnosis and "307" alone is not), and **warns** on a 200 whose body contains a `type="password"` input — the sharp signal for a component-level gate, chosen over matching the words "sign in" because a marketing page routinely *links* to sign-in but should never *contain* a password field, and because a repo may legitimately mark its own `/login` public. Deliberately does NOT use `probeOnce`: that returns `{status}` only by design, and a useful failure here needs the Location header — so it follows `smoke/auth.ts`'s in-package precedent of raw fetch with manual redirect rather than forking the shared transport or widening its contract. SKIPS with no marked routes; **FAILS when routes are marked but no base URL is configured** (`--base-url` → `PORTFOLIO_GATE_PREVIEW_URL` → `PUBLIC_ALIAS`), because an unverified public page is the bug itself. Verified the same way as machine-routes — against ExecutorAI production it passed on the fixed tree, then falsely marking the gated `/dashboard` flipped it to exit 1 with `307 → /login`. In `gate.yml` it is ordered **after** `deploy-status --wait`, so on push it probes the deployment for *this* commit rather than the previous one. **v0.9.0 makes the memory-loop gate usable and honest:** it now **auto-discovers `./memory-loop.config.json`** (previously read only with `--config`, so a bare `--base-url` run bypassed a repo's recorded `memoryLoop:false` opt-out and probed a product that had already declared there was nothing there — SayFix, three times), **prints the resolved target** (URL, identity mode, uid, post-call URL) on every run because three runs were once spent diagnosing a red caused by a misnamed variable pointing at an empty string, surfaces the options the probe gained in convai 0.11.0 (`identityMode`/`conversationId`/`agentId`/`postCallUrl`/`expectDistil`/table-name overrides — `postCallUrl` had been unreachable through the gate, i.e. the check with the most direct security consequence was the one that could not be configured), and renders **`SKIP` at the same weight as `FAIL`**, excluded from the verdict rather than counted green. **v0.12.0 adds `portfolio-gate-audit-first-paint` — does the page a visitor lands on actually SAY anything before the JavaScript arrives?** The sibling question to `public-routes`: that one asks whether a visitor can REACH the page, this asks whether reaching it shows them anything. Kira served three pages behind its three main CTAs as a header, a footer and **sixteen characters** — the SayFix widget's "Report a problem" — while a tester timed 15s of white on the one that asks for a card: *"not a slow page, a broken one, and I have no way to tell the difference."* **Every reachability signal was green and correct**: 200, expected commit, no redirect, so `deploy-status`, `smoke-routes` and `public-routes` all passed over it. **The obvious implementation is the wrong one, and this is the whole design:** those pages were not empty documents — they served full chrome — so "does the response contain visible text" PASSES on the exact defect it was written for (`/plan` scores 180). It therefore measures visible text **outside `<header>`/`<footer>`/`<nav>`**, via a depth-counting scanner rather than a regex, because chrome nests and a non-greedy `<header>.*?</header>` silently under-counts it, reintroducing that false negative. **Passes on enough text OR a real heading** (`≥8` chars, first `h1`/`h2`/`h3` outside chrome) — a sign-in page is legitimately sparse, and a bare character threshold pressures whoever fixes it into padding the page with copy written to satisfy an assertion, which is worse than the defect; *having no way to tell where you are* is the failure, sparseness is not. **No browser needed** (the defect is in the server response, so `fetch` sees exactly what the visitor sees in second one) and it reuses the existing `@public-route` marker rather than inventing a second one nobody remembers. Reachability stays `public-routes`' verdict — a non-200 is skipped here rather than double-counted. First run found a **fourth** blank page no tester had ever seen (`/signup` — the persona would not create an account) and **disproved** the recorded diagnosis for a fifth (`/genome` already server-renders 3,935 chars; the planned "move `'use client'` down" would have changed nothing and been reported as a fix). |
