# Voice Setup — the canonical activation runbook (read before wiring/activating voice on any product)

> **What this is.** The single, portable runbook for **turning the portfolio voice agent ON** in a
> product — the config + env + provisioning + wiring steps, in order. It sits alongside
> `VOICE_MEMORY_STANDARD.md` (the memory-loop rules) and `PRODUCT_STANDARDS.md` §6 (the placement
> gate): those say *what a good voice agent must do*; this says *how to make it exist and go live*.
>
> **Why it exists.** Voice "absent" is almost never missing code — it's an **un-mounted widget** or
> an **un-provisioned agent**. LaunchReady (2026-07-20) shipped the whole `@caistech/discovery-agent`
> stack but the widget was never rendered *and* the agent was never provisioned, so a naive-tester
> correctly reported "voice absent — a promise the product doesn't keep." This runbook makes both
> failure modes a checklist, not a rediscovery.
>
> **Never fork the voice stack.** Voice = `@caistech/discovery-agent` (config-driven interview) built
> on `@caistech/elevenlabs-convai` (provisioning + webhooks + memory loop + the `DiscoveryWidget`).
> Consume them; never hand-roll a voice route/client (that's the retired-legacy-stack mistake).
>
> **Last updated:** 2026-07-20.

## The two failure modes (check BOTH — either one = "voice absent")

1. **Widget not mounted.** The product widget (`DiscoveryWidget`, or a product wrapper like
   LaunchReady's `VoiceIngest`) exists but no page renders it — or it's gated behind an
   `enabled()` flag that's never true. **Fix: render it in the authed flow, gated by the
   activation flag.**
2. **Agent not provisioned.** No ElevenLabs agent id / post-call secret set, so the enable flag is
   correctly `false` and the widget hides. **Fix: run provisioning (below) and set the two env vars.**

A product is only "voice-live" when BOTH are true. Verify with `/voice-auditor` (behavioural — the
widget renders AND the memory loop fires), not just a code grep.

## Two agent patterns — the agent id lives in DIFFERENT places (don't conflate)

| Pattern | What it is | Widget | Agent id lives in |
|---|---|---|---|
| **Guide / clarifier** (the §6 standard in-app agent) | floating chrome coach, "talk it through anywhere" | `<VoiceWidget>` (`@caistech/elevenlabs-convai/react`) | **`voice.config.ts`** (generated by `renderVoiceConfigModule`) — **never a `NEXT_PUBLIC_*` env** |
| **Discovery / interview** | per-prospect interview that extracts structured data | `<DiscoveryWidget>` (`@caistech/discovery-agent/react`) | a server env (`<PREFIX>_VOICE_AGENT_ID`) — a legitimately different pattern |

Getting these backwards is the standard mistake (LaunchReady 2026-07-20 had the guide agent's id in
`NEXT_PUBLIC_ELEVENLABS_AGENT_ID` with no widget mounted — migrated to `voice.config.ts` + `<VoiceWidget>`).

## Env-var scheme (secrets only)

The agent **id** is NOT an env var for the guide agent (it's in `voice.config.ts`). Env carries the
secrets + the discovery-agent id. Per-product prefix (e.g. `REVERSE_SCOUT_`) disambiguates.

| Var | Source | Set as |
|---|---|---|
| `ELEVENLABS_API_KEY` | operator (ElevenLabs account) | Vercel **sensitive**, prod+preview |
| `VOICE_SESSION_SECRET` | operator (random 32+ bytes) | Vercel **sensitive**, prod+preview |
| `<PREFIX>_VOICE_POSTCALL_SECRET` | **provision() output** (the webhook HMAC secret) | Vercel **sensitive**, prod+preview |
| `<PREFIX>_VOICE_AGENT_ID` | provision() output — **discovery agent ONLY** | Vercel prod+preview |

The post-call secret is **extracted at provisioning — never invented, never a phantom
`ELEVENLABS_WEBHOOK_SECRET`.** HMAC verification happens INSIDE the `@caistech` webhook handlers
using this value (do not hand-roll a signature check).

## Activation — the guide agent (single command)

The canonical entry point is **`scripts/voice-init.mjs --provision`** (cais-shared-services
`62e5426`): persona → `provisionVoiceAgent()` → writes the real id into the target's
**`voice.config.ts`**. One command, no hand-carrying an id.

```
node scripts/voice-init.mjs --target ../<Repo> --provision \
  --name "<Product>" --base-url https://<prod-url>      # needs ELEVENLABS_API_KEY; idempotent (adopts by name)
```

Then: **mount the widget** — `import { voiceConfig } from '@/voice.config'` →
`<VoiceWidget {...voiceConfig} />` from `@caistech/elevenlabs-convai/react`, inside a **`'use client'`
wrapper** (a direct import into a server-component layout fails the build: *"createContext is not a
function"*). The scaffold `templates/cais-build-template-v2` (`75103ec`) ships this pre-wired.
**Mounting is the step most often missed — a built-but-unrendered widget is the #1 "voice absent" cause.**

## Activation — the discovery agent

1. Consume `@caistech/discovery-agent` (+ `/react` `DiscoveryWidget`); define the `DiscoveryConfig`
   (persona + stages + extraction schema + `onResult` sink) — see LaunchReady
   `lib/reverse-scout/voice-discovery.ts`.
2. Set `ELEVENLABS_API_KEY` + `VOICE_SESSION_SECRET`; call the product's provision route
   (LaunchReady: `POST /api/admin/reverse-scout/voice/provision`) → returns `{ agentId, webhookSecret }`
   (binds the post-call webhook to `/api/convai/webhooks/*` via `bindWorkspaceWebhook`).
3. Set `<PREFIX>_VOICE_AGENT_ID` + `<PREFIX>_VOICE_POSTCALL_SECRET` from the output; redeploy.
4. Mount `<DiscoveryWidget>` in the flow, gated by the enable flag (`voiceCoachEnabled()`).

## Verify (both patterns)

**Behaviourally** with `/voice-auditor`: the launcher renders, connects (or shows the no-mic text
fallback — degrade-don't-fake), and the memory loop's "welcome-back" recall actually fires. Placement
audited across BOTH portals for a dual-auth product (§6 / §8.5).

- **Rules / behaviour:** `VOICE_MEMORY_STANDARD.md` (the recall→distil→persist loop, HMAC, identity
  server-derived at connect, degrade-don't-fake) + `PRODUCT_STANDARDS.md` §6 (placement gate,

**Gotcha ledger (append as found):**
- 2026-07-20 (LaunchReady) — TWO separate gaps behind one "voice absent": (a) the **guide** agent's
  id was in `NEXT_PUBLIC_ELEVENLABS_AGENT_ID` with **no `<VoiceWidget>` mounted** → migrated to
  `voice.config.ts` + a `ChromeVoice` `'use client'` wrapper on the authed layout; (b) the
  **discovery** widget (`VoiceIngest`) was built but its `voiceEnabled` prop was never consumed by
  `UserNewAssetForm` → mounted, gated by `voiceCoachEnabled()` (still needs the discovery agent
  provisioned). Lesson: a repo can have BOTH agents, each absent for a different reason.
- `<VoiceWidget>` must render inside a `'use client'` module — a direct import into a server-component
  layout fails the build (*"createContext is not a function"*).
- Cookie/webhook: the post-call secret is provision-extracted (`<PREFIX>_VOICE_POSTCALL_SECRET`),
  NOT a hand-created `ELEVENLABS_WEBHOOK_SECRET`; verification is in-package.
